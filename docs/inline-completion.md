# 行内代码补全

本页对应 `代码补全系统实现文档.md` 的实现落地与现状。四期已全部实现，实机验证情况见「验证状态」。

## 怎么用

插件加载后，在编辑器里输入即可触发；补全以幻影文本呈现。

| 操作 | 按键 | 由谁提供 |
| --- | --- | --- |
| 采纳整条 | `Tab` | Monaco 自带 |
| 采纳下一段（按词） | `Ctrl+方向键右` | Monaco 自带 |
| 采纳下一行 | `Ctrl+Alt+方向键右` | 本插件（Monaco 没有这一粒度） |
| 上一条 / 下一条候选 | `Alt+[` / `Alt+]` | Monaco 自带 |
| 关闭建议 | `Esc` | Monaco 自带 |

触发时机由本插件控制（文档 4.1）：换行立即触发，其余按语言防抖（快档 90 ms、慢档 125 ms），
连续输入会作废在途请求。参数由服务端按实验分组下发，客户端不写死。

## 服务端接口

| 方法 | 用途 |
| --- | --- |
| `POST /dsh-vscode/completion` | 补全请求，SSE 返回（`meta` / `output` / `error` / `content_security` / `done`） |
| `completion.config` | 下发实验分组、该组参数、租户安全规则 |
| `completion.telemetry` | 写入埋点（展示 / 采纳 / 取消 / 失败） |
| `completion.stats` | 读取采纳率、取消率、首字节延迟、失败次数与最近失败原因 |
| `completion.index.status` / `completion.index.refresh` | 检索索引状态与重建 |

审计日志写在 `<工作区>/.dsh-workbench/audit.jsonl`：内容安全命中的两种动作（拦截、脱敏）都落一条，
字段含时间、动作、规则标识与名称、会话、文件、语言。该目录被索引自带的 `.gitignore` 排除。

## 环境变量

| 变量 | 作用 |
| --- | --- |
| `DSH_COMPLETION_PROVIDER=local` | 强制走本地兜底提供方（离线或单独验证客户端链路时用） |
| `DSH_COMPLETION_ENDPOINT` | OpenAI 兼容的补全端点基址，例如 `http://127.0.0.1:8080/v1` |
| `DSH_COMPLETION_MODEL` | 上面那个端点使用的模型标识，默认 `completion` |
| `DSH_COMPLETION_API_KEY` | 上面那个端点的密钥，作为 `Authorization: Bearer` 发送 |

选路顺序：`DSH_COMPLETION_PROVIDER=local` → 本地兜底；配了 `DSH_COMPLETION_ENDPOINT` → 该端点；
其余情况用 DSH 的模型服务，不可用时退回本地兜底。

## 验证状态

**已在真实宿主上验证**（本地兜底提供方，浏览器端到端）：

- 幻影文本呈现、整块采纳（真实按键）、候选切换（在两条候选间往返，且切换不重新发起请求）
- 结果过滤与后处理、三级采纳粒度、采纳记账、就近取消
- 检索：结构分块、本地嵌入、按项目索引、片段注入（`meta.snippets` 可观测）
- 内容安全：跨数据块的模式能被抓到（逐块匹配会漏），拦截中止本次补全、脱敏保留内容并标记，
  两种动作都进审计日志
- 实验分组、采纳率 / 取消率 / 首字节延迟统计、失败留痕
- 状态量：174 项单测通过（另有 1 项为既有的 Windows symlink 权限用例，与本功能无关）

**未验证**：

- **DSH 模型提供方的实机调用**。这条路径在本机不起作用，原因是环境而非代码：独立的 `dsh web`
  实例里 DeepSeek Messages 传输直接失败（换 `deepseek-official` 与 `deepseek-account` 两条路由
  结果相同）。桌面端应用进程内的同一条传输是可用的，因此预期在桌面端可用，但这一点尚未实测。
- **真实模型的补全质量**。本地兜底只做标识符补全，质量结论必须来自真实模型。
- **OpenAI 兼容通道的响应解析**。请求能到达上游（本地桩实测），但 DSH 宿主进程内的响应体没有解析出
  文本；同一个提供方在普通 Node 进程里对同一个桩解析正常，所以问题在宿主这一侧，暂未定位。
  这条通道不在生产路径上（生产用 DSH 模型服务）。

失败一旦发生会留下痕迹：`completion.stats` 的 `failed` 与 `lastFailure` 会写明路由与原因
（例如 `completion upstream failed (deepseek-official/deepseek-flash): …`）。

## 已知局限（文档第九节）

1. 补全质量主要取决于模型与 prompt，不取决于客户端代码。客户端做的是把上下文准备好并按契约收发。
2. prompt 设计没有通用最优解：序列结构、字段顺序、截断策略都需要按目标模型实测。
3. 检索质量取决于嵌入模型与分块策略。本实现用哈希嵌入（256 维）做兜底，相似度阈值因此按实测调到
   0.15，而不是文档建议的 0.7（后者对应真实嵌入模型）。
4. 多模型融合是可选路径，本实现未做。
5. 长上下文不等于高相关：预算分配按优先级丢弃实现，符号上下文上限为总预算的 10%。
6. 内容安全与隐私需要显式设计。当前实现不上传代码到第三方，检索索引只落在工作区本地目录；
   请求前预过滤会按拦截规则阻止内容离开本机。
7. 检索索引默认落在 `<工作区>/.dsh-workbench/index.json`（自带 `.gitignore`）。若不想在工作区留文件，
   需要改到宿主存储域 —— 这一点尚未决定。
8. `output` 事件的候选序号由提供方给出：逐字流式的模型把同一条候选拆成多块，这些块共用同一个序号。

## 与文档建议的几处偏离

以下都是有意选择，不是遗漏；列出来是为了让人能按同一份文档核对：

| 文档建议 | 本实现 | 原因 |
| --- | --- | --- |
| 增量解析器（tree-sitter 一类）抽取模块/类/函数三级实体 | 按大括号与缩进抽窗口分块，正则是实体边界 | 零依赖是硬约束（不允许为此新增依赖）；实体名与签名靠分块正文自带 |
| 本地嵌入模型 + SQLite 向量扩展 | 哈希嵌入（256 维）+ JSON 文件 | 同上；索引体积与延迟已在性能分析目录实测 |
| 每项目分库、周期重建以小时或天计 | 每工作区一份索引，周期 24 小时 | 与文档一致，仅存储形态不同 |
| 服务端维护模型清单，按语言/分组/等级下发 | 配置接口下发单个模型与分组参数 | 清单是能力不是必需；当前只有一条选路 |
| 进程间 IPC + JSON-RPC | HTTP（API 路由 + SSE） | 分层与边界一致：编辑器在浏览器渲染进程，组装与检索在宿主进程 |

分块去重（文档 5.2 的实体去重）已实现：同一段内容只入库一次，因此同样的分块预算下能容纳更多不同文件
（实测入库文件数由 2587 升到 2776）。
